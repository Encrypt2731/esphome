  Wiring notes

  - Each DS18B20 data pin needs a 4.7kΩ resistor between data and 3.3V — the
    H2's internal pull-up is too weak for reliable 1-Wire.
  - 4-pin PC fans: connect GND → GND, +12V → fan power rail, PWM pin →
    GPIO10/11. The H2 outputs 3.3V logic which most fan controllers accept;
    check your fan's spec sheet.
  - The relay restore_mode: RESTORE_DEFAULT_OFF means it stays off after a power
    cycle unless HA explicitly turns it on — safe for most automation setups.
  - If HA doesn't find the device via Bluetooth, consider adding a second ESP32
    (any WiFi variant) configured as a bluetooth_proxy to bridge it.

  ---

  Practical tradeoffs to consider

  - OTA is the biggest gotcha — without WiFi or BLE, you lose easy over-the-air
    updates. Plan for physical access to reflash.
  - If you already have a Zigbee network (lights, sensors, etc.), this
    integrates cleanly with no extra hardware.
  - If this is your only Zigbee device, buying a coordinator just for one fan
    controller is more overhead than it's worth — BLE is simpler.
  - The ESPHome Zigbee component is newer and less mature than its WiFi/BLE
    counterparts; check the ESPHome Zigbee docs
    (https://esphome.io/components/zigbee.html) for the current cluster API as
    it's been evolving.

  ---

  Two things worth calling out:

  - Safety cutoff — the 30-minute auto-off on on_turn_on is intentional. If HA
    loses the Zigbee connection mid-schedule, the valve won't run indefinitely.
    Adjust the delay to suit your longest expected zone runtime, or remove it if
    your HA automations already handle this.
  - RESTORE_DEFAULT_OFF — the relay always starts off on power cycle, so a
    controller reboot can't accidentally open the valve.

> Is there a way to impose a fallback irrigation schedule that is embedded into
  the script, that will take over if the ESP32-H2 cannot phone home to the
  home assistant server?

  Thought for 1m 11s (ctrl+o to expand)

● Yes — the cleanest approach is a heartbeat watchdog: HA toggles a dedicated
  switch every hour, and the device counts hours since the last ping. If the
  count exceeds the threshold, a fallback schedule takes over.

  Key limitation: The ESP32-H2 has no WiFi, so there's no NTP. Without a
  hardware RTC module the device can't know the time of day — the fallback runs
  on an interval (every 24h) rather than at a specific time like 6am.

  ---

  esphome:
    name: irrigation-controller
    friendly_name: Irrigation Controller

  esp32:
    board: esp32h2devkitm
    variant: esp32h2
    framework:
      type: esp-idf

  logger:
    level: INFO

  substitutions:
    heartbeat_timeout_h: "25"   # Hours without HA contact before fallback
  activates
    fallback_interval_h: "24"   # Minimum hours between fallback irrigation runs
    safety_cutoff: "30min"      # Maximum single run duration (both HA and
  fallback)

  zigbee:
    endpoints:
      - num: 1
        device_type: ON_OFF_OUTPUT
        cluster_list:
          - id: ON_OFF
            attributes:
              - attr_id: ON_OFF
                value_ref: irrigation_relay

      # HA pings this every hour to prove it's alive; any state change resets
  the counter
      - num: 2
        device_type: ON_OFF_OUTPUT
        cluster_list:
          - id: ON_OFF
            attributes:
              - attr_id: ON_OFF
                value_ref: ha_heartbeat

  globals:
    - id: hours_no_heartbeat
      type: int
      restore_value: no
      initial_value: '0'

    - id: hours_since_watered
      type: int
      restore_value: no
      initial_value: '0'

  switch:
    - platform: gpio
      pin: GPIO2
      id: irrigation_relay
      name: "Irrigation"
      icon: "mdi:sprinkler"
      restore_mode: RESTORE_DEFAULT_OFF
      on_turn_on:
        - globals.set:
            id: hours_since_watered
            value: '0'
        - logger.log: "Irrigation started"
        - delay: $safety_cutoff
        - switch.turn_off: irrigation_relay
        - logger.log: "Irrigation stopped by safety cutoff"

    - platform: template
      name: "HA Heartbeat"
      id: ha_heartbeat
      optimistic: true
      restore_mode: RESTORE_DEFAULT_OFF
      on_turn_on:
        - globals.set:
            id: hours_no_heartbeat
            value: '0'
      on_turn_off:
        - globals.set:
            id: hours_no_heartbeat
            value: '0'

  interval:
    - interval: 1h
      then:
        - lambda: |-
            id(hours_no_heartbeat) += 1;
            id(hours_since_watered) += 1;

            if (id(hours_no_heartbeat) >= $heartbeat_timeout_h
                && id(hours_since_watered) >= $fallback_interval_h
                && !id(irrigation_relay).state) {
              id(irrigation_relay).turn_on();
            }

  How it behaves

  ┌──────────────────────┬──────────────────────────────────────────────────┐
  │       Scenario       │                      Result                      │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ HA online, sending   │ hours_no_heartbeat never reaches 25 — fallback   │
  │ heartbeats           │ never fires                                      │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ HA offline for 25h+  │ Fallback triggers; irrigates for up to 30min,    │
  │                      │ then repeats every 24h                           │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ HA comes back online │ Heartbeat resets counter; HA resumes normal      │
  │                      │ control                                          │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ Device reboots       │ Both counters reset to 0; fallback won't fire    │
  │                      │ for at least 25h, giving HA time to reconnect    │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ Relay already        │ !id(irrigation_relay).state guard prevents       │
  │ running when         │ double-trigger                                   │
  │ fallback checks      │                                                  │

> can you please explain how the code works in relation to the temperature
  curve and fan speed mechanism

  Thought for 3s (ctrl+o to expand)

● The four curve parameters

  The shape of the curve is defined by four values:

  substitutions:
    default_temp_low: "30.0"     # point A — where ramping begins
    default_temp_high: "60.0"    # point B — where fans hit 100%
    default_fan_min_pct: "20.0"  # floor speed (never drops below this)
                                 # ceiling is implicitly always 100%

  Plotted, it looks like this:

  100% |                        ,----------
       |                   ,---'
       |               ,--'
   20% |  ,-----------'
       |
       +--+----------+-----------+----------> °C
          0         30          60

  ---

  What happens on every temperature reading

  Every 10 seconds each DS18B20 fires on_value, which runs this lambda (same
  logic for both fans):

  float t     = x;                              // current temperature reading
  float t_low = id(curve_temp_low).state;       // 30.0 by default
  float t_high = id(curve_temp_high).state;     // 60.0 by default
  float f_min = id(curve_fan_min_pct).state / 100.0f;  // 0.20 by default

  Then one of four branches decides the output level:

  if (isnan(t))         spd = 1.00f;   // ① sensor fault → full speed (failsafe)
  else if (t <= t_low)  spd = f_min;   // ② below ramp → minimum speed (0.20)
  else if (t >= t_high) spd = 1.00f;   // ③ above ramp → full speed (1.00)
  else                  spd = f_min + (t - t_low) / (t_high - t_low) * (1.0f -
  f_min);
                                        // ④ within ramp → linear interpolation

  Branch ④ is the core formula. Breaking it down with concrete numbers (t =
  45°C, defaults):

  (t - t_low)               = 45 - 30  = 15      ← how far into the ramp you are
  (t_high - t_low)          = 60 - 30  = 30      ← total ramp width
  ratio                     = 15 / 30  = 0.50    ← 50% of the way through the
  ramp
  (1.0 - f_min)             = 1.0 - 0.20 = 0.80  ← available headroom above
  minimum
  spd = 0.20 + 0.50 * 0.80  = 0.20 + 0.40 = 0.60 → 60%

  ---

  How that percentage becomes actual fan speed

  The spd value (0.0–1.0) is passed directly to the LEDC output:

  id(fan1_output).set_level(spd);

  LEDC (the ESP32's hardware PWM peripheral) translates this into a 25 kHz PWM
  signal where the duty cycle matches spd. A 4-pin PC fan reads that duty cycle
  on its dedicated PWM pin and sets its motor speed accordingly — 0.60 → 60%
  duty cycle → fan runs at ~60% of max RPM.

  25 kHz PWM at 60% duty:
  |‾‾‾‾‾‾|    |‾‾‾‾‾‾|    |‾‾
  |      |    |      |    |
  +------+----+------+----+--
    60%   40%   60%   40%

  ---

  What HA can change at runtime

  Because the curve parameters are number entities with restore_value: true, HA
  can write new values to them via Zigbee at any time. The lambda always reads
  them live from .state, so the new curve takes effect on the very next
  temperature reading — no reboot needed.

  If HA goes offline for 25+ hours the heartbeat watchdog fires number.set to
  push all three parameters back to the substitutions defaults, which also
  overwrites the flash — so a reboot while HA is still offline starts up with
  the safe defaults rather than the last HA-customised values.

> the default temperature curve seems bumpy - is it possible to make it operate
  more smoothly?

  Thought for 21s (ctrl+o to expand)

● The current linear ramp has two sharp corners — at 30°C where it transitions
  from flat-to-ramping, and at 60°C where it transitions from ramping-to-flat.
  Those are points where the rate of change snaps suddenly, which the fans feel
  as abrupt speed changes.

  Current (linear):          Smoothstep:

  100% |         ,-------    100% |           ,-------
       |        /                 |         ,'
       |       /                  |       ,'
       |      /                   |     ,'
   20% |-----'                20% |---,'
       |                          |
       +---+------+------->        +---+------+------->
          30     60                   30     60
           ^ corner                    ^ smooth

  The fix is smoothstep — a standard S-curve formula that eases in and out at
  both endpoints, giving zero slope at the transition points so there are no
  corners at all.

  Only the lambda changes. Replace it in both sensor blocks:

  float t     = x;
  float t_low = id(curve_temp_low).state;
  float t_high = id(curve_temp_high).state;
  float f_min = id(curve_fan_min_pct).state / 100.0f;
  float spd;

  if (isnan(t)) {
      spd = 1.00f;
  } else {
      // Clamp temperature to the 0..1 range between the two setpoints
      float norm = (t - t_low) / (t_high - t_low);
      norm = fmaxf(0.0f, fminf(1.0f, norm));
      // Smoothstep: 3t² - 2t³  — zero slope at both endpoints
      float curve = norm * norm * (3.0f - 2.0f * norm);
      spd = f_min + curve * (1.0f - f_min);
  }

  id(fanX_output).set_level(spd);
  id(fanX_speed).publish_state(spd * 100.0f);

  The clamp + smoothstep approach also removes the three if/else branches from
  the original — the clamp handles the boundary cases implicitly, so the code is
  shorter as well as smoother.

  ---

  How the smoothstep formula behaves at key points:

  ┌─────────────┬──────┬───────┬─────────────────────┐
  │ Temperature │ norm │ curve │ Fan speed (20% min) │
  ├─────────────┼──────┼───────┼─────────────────────┤
  │ ≤ 30°C      │ 0.00 │ 0.000 │ 20%                 │
  ├─────────────┼──────┼───────┼─────────────────────┤
  │ 35°C        │ 0.17 │ 0.069 │ 25%                 │
  ├─────────────┼──────┼───────┼─────────────────────┤
  │ 45°C        │ 0.50 │ 0.500 │ 60%                 │
  ├─────────────┼──────┼───────┼─────────────────────┤
  │ 55°C        │ 0.83 │ 0.931 │ 95%                 │
  ├─────────────┼──────┼───────┼─────────────────────┤
  │ ≥ 60°C      │ 1.00 │ 1.000 │ 100%                │
  └─────────────┴──────┴───────┴─────────────────────┘

  The midpoint (45°C) still maps to 60%, same as before — the curve is
  symmetric, just with rounded shoulders instead of sharp corners.

> Does this smoothstep change also apply for HA dictated variables?

● Yes, it applies automatically regardless of where the curve parameters come
  from.

  The lambda reads the curve parameters at runtime via .state on every
  temperature reading:

  float t_low = id(curve_temp_low).state;
  float t_high = id(curve_temp_high).state;
  float f_min  = id(curve_fan_min_pct).state / 100.0f;

  - HA via Zigbee — written to the number entities

● Yes — there is a meaningful difference between the two configs worth flagging.

  The irrigation config uses RESTORE_DEFAULT_OFF, which is appropriate because
  the relay is wired to NO terminals. On power-on the coil is de-energized, NO
  contacts stay open, valve stays closed. Safe.

  The fan controller relay uses ALWAYS_OFF, wired to NC terminals. On power-on
  the coil is de-energized, NC contacts stay closed, circuit stays connected.
  That is the intended behaviour and is safe for the relay itself.

  However, there is a subtler risk depending on what is connected to that relay
  circuit:

  When power is restored after a cut, the ESP32-H2 boots and the relay circuit
  is immediately closed — before Zigbee has reconnected and before HA has had
  any chance to assess whether the circuit should be closed at that moment. If
  HA had issued an open command shortly before the power cut, the device has no
  memory of that instruction (ALWAYS_OFF deliberately discards it) and will
  close the circuit regardless.

  Whether this is a problem depends entirely on what the relay is switching:

  ├───────────────────────────────┼─────────────────────────────────────────┤

  │ passive device                │ harmless                                │
  ├───────────────────────────────┼─────────────────────────────────────────┤

● There are two distinct aspects to address here.

  ---

  Software — the current design is already correct

  From a software perspective, the current config already satisfies the
  requirement. The only ESPHome event that turns the relay ON (which with NC
  wiring opens the circuit) is an explicit HA command via Zigbee. Every other
  event keeps or returns the relay to OFF:

  ┌───────────────────────┬──────────────────┬──────────────────┐
  │         Event         │   Relay state    │     Circuit      │
  ├───────────────────────┼──────────────────┼──────────────────┤
  │ Boot / power restore  │ OFF (ALWAYS_OFF) │ Closed ✓         │
  ├───────────────────────┼──────────────────┼──────────────────┤
  │ HA command            │ ON               │ Opens (intended) │
  ├───────────────────────┼──────────────────┼──────────────────┤
  │ auto_reconnect fires  │ OFF              │ Closes ✓         │
  ├───────────────────────┼──────────────────┼──────────────────┤
  │ Power cut mid-session │ OFF on restore   │ Closes ✓         │
  └───────────────────────┴──────────────────┴──────────────────┘

  No config change is needed here.

  ---

  Hardware — there is a genuine boot-time risk

  Before the firmware initialises, the ESP32-H2's GPIO pins are in an undefined
  floating state. GPIO2 could briefly float HIGH during the ROM boot phase —
  before ALWAYS_OFF has taken effect — momentarily energising the relay coil and
  opening the NC contacts. For a high-criticality application this is
  unacceptable.

  The fix is a hardware one: add a 10kΩ pull-down resistor between GPIO2 and
  GND. This holds the pin at LOW at the silicon level throughout the entire boot
  sequence, regardless of firmware state, making it physically impossible for
  the coil to energise until the firmware deliberately drives the pin HIGH.

  There is a secondary concern: GPIO2 on the ESP32-H2 is the MTMS JTAG pin. Some
  devkit boards place a pull-up on JTAG pins for debugging purposes. If your
  board has a pull-up on GPIO2, that pull-up would work directly against the
  safety requirement. It is worth checking your specific board's schematic.

  If the schematic confirms a pull-up on GPIO2, the clean resolution is to move
  the relay to GPIO3, which is a general-purpose IO with no JTAG or strapping
  function. The only config change required would be:

    - platform: gpio
      pin: GPIO3        # was GPIO2

  Would you like the config file updated to use GPIO3?
