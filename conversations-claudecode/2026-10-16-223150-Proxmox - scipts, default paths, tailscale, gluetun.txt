  that it can be accessed by other devices on my tailnet?

● This is more of a Proxmox/Tailscale setup question than a coding task, but
  here's the process:

  ---

  1 — Open the container's console

  In the Proxmox web UI, click your LXC container → Console

  ---

  2 — Install Tailscale

  curl -fsSL https://tailscale.com/install.sh | sh

  ---

  3 — Start and authenticate Tailscale

  tailscale up

  This outputs an authentication URL — open it in your browser and log in to
  your Tailscale account to approve the device.

  ---

  4 — Verify it's connected

  tailscale ip

  This should return a 100.x.x.x Tailscale IP that other devices on your tailnet
  can use to reach it.

  ---

  Important — LXC-specific requirement:

  Unprivileged LXC containers (which is what the Paperless-NGX script creates)
  need a TUN device to run Tailscale. Without it, tailscale up will fail. Fix it
  from the Proxmox host shell:

  # Replace 100 with your container's ID
  echo 'lxc.cgroup2.devices.allow = c 10:200 rwm
  lxc.mount.entry = /dev/net/tun dev/net/tun none bind,create=file' >>
  /etc/pve/lxc/100.conf

  Then restart the container:
  pct restart 100

  After that, re-run tailscale up inside the container.

> How do I tag the network traffic for a particular container so that it only
  goes via a particular vlan (say VLAN 20)

● This is configured on the Proxmox host, not inside the container. In Proxmox,
  VLANs are handled at the network bridge level.

  ---

  Via the Proxmox GUI:

  1. Click your container → Network
  2. Click the existing network interface (e.g. eth0)
  3. Set the VLAN Tag field to 20
  4. Click OK then restart the container

  ---

  Or directly in the container's config file from the Proxmox host shell:

  nano /etc/pve/lxc/100.conf

  Find the net0 line and add tag=20:

  net0: name=eth0,bridge=vmbr0,hwaddr=XX:XX:XX:XX:XX:XX,ip=dhcp,tag=20,type=veth

  Then restart:
  pct restart 100

  ---

  Prerequisites:

  - Your physical switch port connected to the Proxmox host must be configured
    as a trunk port that carries VLAN 20
  - The Proxmox bridge (vmbr0) must have VLAN-aware enabled — check this under
    your node → Network → click vmbr0 → ensure VLAN aware is ticked
  - Your router/firewall must have VLAN 20 configured with a DHCP server if
    you're using DHCP

> how does the network traffic for all the other containers get treated
  (Assuming they are not tagged like the container above)?

● Untagged traffic (containers without a tag= on their net0 line) travels on the
  native/untagged VLAN of the bridge — typically referred to as VLAN 1 or
  whatever your switch treats as the default untagged VLAN on that trunk port.

  So in practice:

  ┌───────────────┬─────────┬────────────────────────────────────┐
  │   Container   │ Tag set │          Traffic lands on          │
  ├───────────────┼─────────┼────────────────────────────────────┤
  │ Paperless-NGX │ tag=20  │ VLAN 20                            │
  ├───────────────┼─────────┼────────────────────────────────────┤
  │ All others    │ none    │ Native/untagged VLAN (e.g. VLAN 1) │
  └───────────────┴─────────┴────────────────────────────────────┘

  ---

  One thing to be aware of: if your other containers are on the native VLAN and
  your VLAN 20 container is on a separate subnet, they won't be able to talk to
  each other directly unless your router/firewall has inter-VLAN routing enabled
  and a rule permitting it.

  This is actually a common reason to use VLANs in a home lab — isolating
  certain services (like a NAS-connected document manager) from the rest of your
  containers.

> Why does the Unifi OS Server need to be in a privileged container or VM?

  Thought for 11s (ctrl+o to expand)

● The core reasons come down to low-level system access that unprivileged LXC
  containers cannot provide:

  ---

  1 — Docker-in-LXC
  UniFi OS runs its applications (Network, Protect, Access, etc.) inside Docker
  containers. Running Docker inside an unprivileged LXC container requires
  nested containerization that the kernel blocks by default — privileged mode
  (or a VM) removes that restriction.

  2 — Raw socket access for device adoption
  UniFi discovers and adopts devices using L2 broadcast packets and raw network
  sockets. Unprivileged containers have restricted access to the network stack,
  which breaks device discovery and adoption.

  3 — iptables / nftables manipulation
  UniFi OS manages firewall rules and NAT for the network it controls. Writing
  iptables rules requires kernel-level network access that is denied to
  unprivileged containers.

  4 — Kernel module loading
  Features like WireGuard VPN and certain switching functions may need to load
  kernel modules — something unprivileged containers cannot do.

  5 — MongoDB requirements
  The database backend has memory management requirements (e.g.
  vm.max_map_count) that require writing to /proc/sys, which is read-only inside
  unprivileged containers.

  ---

  Why a VM sidesteps all of this
  A VM gets its own full kernel, so none of these restrictions apply — it's the
  cleanest option if you want full isolation without the complexity of a
  privileged container. The tradeoff is more RAM and CPU overhead compared to an
  LXC container.

    and forwarding between containers at the Proxmox network level

  Which setup are you using?

> let's go with docker

● The key is network_mode: "service:gluetun" in your docker-compose file. This
  makes qBittorrent share Gluetun's network namespace entirely, so all its
  traffic is forced through the VPN tunnel.

  services:
    gluetun:
      image: qmcgaw/gluetun
      container_name: gluetun
      cap_add:
        - NET_ADMIN
      devices:
        - /dev/net/tun:/dev/net/tun
      environment:
        - VPN_SERVICE_PROVIDER=your_provider
        - VPN_TYPE=wireguard          # or openvpn
        - WIREGUARD_PRIVATE_KEY=xxx
        - WIREGUARD_ADDRESSES=xxx
      ports:
        - 8080:8080    # qBittorrent web UI - ports must be declared HERE not on
  qbittorrent
        - 6881:6881    # qBittorrent torrent port TCP
        - 6881:6881/udp
      restart: unless-stopped

    qbittorrent:
      image: lscr.io/linuxserver/qbittorrent
      container_name: qbittorrent
      network_mode: "service:gluetun"   # ← the critical line
      depends_on:
        - gluetun
      environment:
        - PUID=1000
        - PGID=1000
        - TZ=Europe/London
        - WEBUI_PORT=8080
      volumes:
        - ./config:/config
        - /mnt/nas/downloads:/downloads
      restart: unless-stopped

  ---

  Key points:

  - Ports must be declared on the Gluetun service, not qBittorrent — since
    qBittorrent has no network of its own, port mappings on it are ignored
  - depends_on ensures Gluetun starts first, but doesn't guarantee the VPN
    tunnel is up before qBittorrent starts — Gluetun has a built-in health check
    you can use for that
  - If Gluetun goes down, qBittorrent loses all connectivity automatically —
    this is the kill switch behaviour you want

  To verify traffic is routing through the VPN once running:
  docker exec -it qbittorrent curl ifconfig.me
  That should return your VPN provider's IP, not your home IP.
