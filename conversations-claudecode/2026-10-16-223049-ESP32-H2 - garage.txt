  Relay safety (three independent layers):
  1. output.restore_value: false — GPIO pin is always LOW on boot, regardless of
     prior state
  2. switch.restore_mode: ALWAYS_OFF — switch state is never persisted to
     flash/NVS
  3. on_turn_on automation — relay self-closes for exactly 300 ms then releases;
     HA cannot hold it on because the Zigbee On/Off attribute immediately
     resets to OFF

  Door sensor: Uses an internal pull-up so no external resistor is needed.
  inverted: true means a closed circuit (magnet present = door closed) reports
  as the "Closed" state. A 50 ms debounce filter blocks false triggers from
  contact bounce.

  Two Zigbee endpoints:
  - Endpoint 1 — On/Off Output (0x0051): HA sees a switch; sending "turn on"
    fires the pulse
  - Endpoint 2 — IAS Zone / contact_switch (0x0402): HA sees a garage door
    contact sensor

  Two things to adjust before flashing:
  - GPIO8 → your relay IN pin
  - GPIO3 → your sensor input pin

  One caveat: ESPHome's Zigbee component API is under active development. The
  cluster_id / component binding syntax in the zigbee: block should be verified
  against the current ESPHome Zigbee docs
  (https://esphome.io/components/zigbee.html) for your installed version before
  building.

● Looking at this carefully, the honest answer is: mostly yes, with one
  important caveat worth understanding.

  The three software layers all hold on reboot

  ┌────────────────────────┬────────────────────────────┬───────────────────┐
  │         Layer          │        What it does        │   When it runs    │
  ├────────────────────────┼────────────────────────────┼───────────────────┤
  │ restore_value: false   │ GPIO initialises LOW as    │ Very early in     │
  │ on the output          │ part of component setup    │ firmware boot     │
  ├────────────────────────┼────────────────────────────┼───────────────────┤
  │ restore_mode:          │ ESPHome never reads a      │ During component  │
  │ ALWAYS_OFF on the      │ saved ON state from NVS    │ setup             │
  │ switch                 │                            │                   │
  ├────────────────────────┼────────────────────────────┼───────────────────┤
  │ on_boot: priority: 600 │ Explicitly calls           │ Early boot, after │
  │                        │ output.turn_off            │  output is set up │
  └────────────────────────┴────────────────────────────┴───────────────────┘

  All three run before any Zigbee stack activity, so during a software reboot
  the relay is definitively safe.

  The real risk: the hardware window before firmware runs

  Between the moment power is applied and the moment the ESP-IDF firmware
  configures the GPIO as an output (a window of tens of milliseconds), the pin
  is in its hardware reset state — not driven by firmware at all.

  This matters because GPIO8 on the ESP32-H2 is a strapping pin. Strapping pins
  have internal pull-ups or pull-downs that determine chip boot mode. If GPIO8
  has an internal pull-up during reset, and your relay module is active-HIGH (as
  noted in the config), the relay coil could briefly energise for those few
  milliseconds before firmware takes control.

  What to do

  Two fixes, ideally both:

  1. Move the relay to a non-strapping GPIO — on ESP32-H2 the strapping pins are
  GPIO2, GPIO8, and GPIO9. Use GPIO4, GPIO5, GPIO10, or GPIO11 instead.

  2. Add a 10 kΩ pull-down resistor between the relay IN pin and GND. This is a
  hardware guarantee: the relay input is held LOW by physics, independent of
  firmware, even if the GPIO is floating or pulled up internally during reset.

  ESP32-H2 GPIO → [10kΩ to GND] → Relay IN

  That resistor costs a fraction of a cent and makes the relay unconditionally
  safe during any power state. With it in place, even a strapping pin with an
  internal pull-up cannot overcome the pull-down enough to drive the
  optocoupler/transistor in a typical relay module.

  Summary: The config is safe against firmware-driven energisation. For true
  hardware-level safety, change the relay pin away from GPIO8 and add a
  pull-down resistor.
