● Looking at the opened file and your request, let me address a few important
  technical constraints before diving in.

  Important: ESP32-H2 Limitations

  The ESP32-H2 has no WiFi — it only has IEEE 802.15.4 (Zigbee/Thread) and BLE.
  Standard ESPHome uses WiFi for OTA and API, so you must use ESPHome's Zigbee
  mode, which reports data to Home Assistant via a Zigbee coordinator (e.g.,
  Sonoff Zigbee 3.0 USB Dongle Plus). This is supported but still maturing.

  If you want a simpler path, consider an ESP32-C3 or ESP32 classic with WiFi
  instead — same SPI for CC1101, much more ESPHome community support.

  ---

  Wiring: CC1101 Module → ESP32-H2

  CC1101 pre-made modules (the common 8-pin green PCB) run at 3.3V — directly
  compatible with the ESP32-H2's GPIO logic.

  Discovery Workflow

  1. Flash the config and open the ESPHome serial log.
  2. Press your doorbell button — with dump: all, the receiver will print the
     raw protocol and code (e.g., RC switch: protocol 1, data 0x1234AB).
  3. Use that captured code to write a specific remote_receiver binary sensor
     trigger instead of template.
  4. Remove dump: all once you have the code.

  Caveats

  - Zigbee + CC1101 concurrently on ESP32-H2 is unusual. The Zigbee radio uses
    the 802.15.4 stack internally and the CC1101 uses SPI — different
    peripherals, so they should not conflict, but this combination has limited
    community examples. Test RF receive performance in the presence of Zigbee
    transmissions.
  - ESPHome's zigbee: component syntax is still evolving — cross-check against
    the current ESPHome docs before building.
  - Some 433MHz chime protocols (e.g., Byron SX) decode cleanly with ESPHome's
    built-in remote_receiver dumpers; others may need raw timing analysis.

● Decoupling Capacitor Wiring — Detailed

  What they do and why placement matters

  Decoupling capacitors suppress voltage rail noise. The CC1101 draws sudden
  bursts of current during SPI transactions and RF switching, which causes brief
  voltage dips on the 3.3V rail. Without local capacitance to supply that
  charge instantly, the dip can corrupt SPI reads or cause erratic RF behaviour.

  Shorter leads = better. A capacitor 10 cm away connected by long wire has too
  much inductance to respond fast enough — it effectively stops working at high
  frequencies.

  Practical tip

  Most pre-made CC1101 modules already have a small capacitor soldered on the
  PCB near the VCC pin. Even so, add the external 100nF — it handles the
  inductance of your connecting wires that the on-board cap cannot. Think of the
  on-board cap as protecting the chip, and your external cap as protecting the
  wire run from the ESP32-H2 to the module.

  #              │              │ The CC1101 and its module PCB are not 5V

  #   MISO (SO)  │ GPIO6        │ SPI data: CC1101 → ESP32-H2

  -----------------------------------------------------------------------------
  # DECOUPLING CAPACITOR WIRING
  #
  -----------------------------------------------------------------------------
  #
  # Decoupling capacitors suppress voltage rail noise caused by the CC1101
  # drawing sudden bursts of current during SPI transactions and RF switching.
  # Without them, these current spikes cause brief voltage dips that can corrupt
  # SPI reads or produce erratic RF behaviour.
  #
  # KEY RULE: shorter leads = better performance.
  # A capacitor placed 10 cm away via long wires has too much inductance to
  # respond fast enough at high frequencies — it effectively stops working.
  # Place capacitors as physically close to the relevant pins as possible.
  #
  #
  # CAPACITOR 1 — 100nF ceramic (high-frequency bypass)
  # ────────────────────────────────────────────────────
  # Purpose:  Filters fast, high-frequency switching noise generated by the
  #           CC1101 chip itself during SPI and RF activity.
  # Value:    100nF (0.1µF)
  # Type:     Ceramic — NOT polarised. Either leg can go to VCC or GND.
  # Rating:   10V minimum (16V or 25V parts are equally fine)
  # Connect:  Between the CC1101 module's VCC pin and the CC1101 module's GND
  pin
  # Placement: As close to the module's VCC pin as physically possible.
  #           On a breadboard, insert the capacitor legs into the same two rows
  #           as the module's VCC and GND pins — directly adjacent, not at the
  #           far end of the power rail strip.
  #
  # Note: most pre-made CC1101 modules already have a small capacitor soldered
  # on the PCB near the VCC pin. Add this external 100nF anyway — it handles
  # the inductance of your connecting wires that the on-board cap cannot.
  #
  #
  # CAPACITOR 2 — 10µF electrolytic (bulk charge reservoir)
  # ─────────────────────────────────────────────────────────
  # Purpose:  Provides a local charge reservoir to supply the sudden current
  #           demand when the CC1101 powers up its TX/RX circuitry. Prevents
  #           sag on the 3.3V rail that would affect the ESP32-H2 as well.
  # Value:    10µF
  # Type:     Electrolytic — POLARISED. Polarity MUST be correct or the
  #           capacitor will fail, potentially with heat or rupture.
  # Rating:   10V minimum
  # Connect:  Between the ESP32-H2's 3.3V output pin and GND
  # Placement: Close to where the 3.3V wire leaves the ESP32-H2 board toward
  #           the CC1101 module.
  #
  # POLARITY — CRITICAL:
  #   Longer leg  (+) positive → connect to 3.3V
  #   Shorter leg (−) negative → connect to GND
  #   The negative leg is also marked with a white stripe printed on the
  #   side of the cylindrical body of the capacitor.
  #
  #
  # BREADBOARD LAYOUT (top-down view, simplified)
  # ──────────────────────────────────────────────
  #
  #  ESP32-H2 DevKitM-1
  #  ┌───────────────────────────┐
  #  │ 3.3V ─────────────────────┼──┬───────────────────── C2(+)─C2(−)─┐
  #  │                           │  │                                    │
  #  │ GND  ─────────────────────┼──┼────────────────────────────────────┘
  #  │                           │  │                        (C2 = 10µF
  electrolytic,
  #  │ GPIO4 (SCK)  ─────────────┼──┼──── CC1101 SCK          sits near 3.3V/GND
  #  │ GPIO5 (MOSI) ─────────────┼──┼──── CC1101 MOSI         rail on the board)
  #  │ GPIO6 (MISO) ─────────────┼──┼──── CC1101 MISO
  #  │ GPIO2 (CSN)  ─────────────┼──┼──── CC1101 CSN
  #  │ GPIO7 (GDO0) ─────────────┼──┼──── CC1101 GDO0
  #  └───────────────────────────┘  │
  #                                 │     CC1101 VCC ──┬── 3.3V rail
  #                                 └─────────────────┘
  #                                       CC1101 GND ──── GND rail
  #                                             │
  #                                        C1 (100nF ceramic)
  #                                        sits directly between
  #                                        the CC1101 VCC and GND
  #                                        rows on the breadboard
  #
  #
  =============================================================================

  # RF Receiver — decodes incoming 433 MHz signals from the chime transmitter
  #
  -----------------------------------------------------------------------------
  # The remote_receiver component watches the GDO0 pin for pulse-width-modulated
  # digital transitions that represent the demodulated RF baseband signal.
  # It can decode many common protocols automatically (RC switch, LaCrosse,
  # etc.) and will also dump unknown signals as raw microsecond timings.
  remote_receiver:
    pin:
      number: GPIO7
      # GDO0 idles LOW when no signal is present; the CC1101 drives it HIGH
      # during reception. No pull-up or pull-down resistor is needed on this
      # pin — the CC1101 actively drives it both ways.
      inverted: false

                # including its decoded protocol name and code value, or raw
                # pulse timings if the protocol is unrecognised.

                # log. Note the protocol (e.g. "RC switch protocol 1") and the
                # hex/decimal code. Once captured, you can replace dump: all

    tolerance: 50%  # How much timing variation is accepted when matching pulses
                    # to a known protocol. Battery-powered RF remotes and cheap
                    # oscillators can drift significantly — 50% is permissive
                    # enough to catch most real-world devices without causing
                    # false positives on a 433 MHz band that is fairly busy.

                    # reach the protocol decoder. Raise to 8–10 us if you get

                    # Most 433 MHz OOK protocols send a sync gap of 5–10 ms
                    # between repeated frames; 4 ms balances responsiveness
                    # against splitting a multi-frame burst into false events.
